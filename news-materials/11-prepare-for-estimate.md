# Публикация 11 — без обложки

**Дата публикации:** 2026-10-13 (13.10.2026)

## Русская версия

**Заголовок:** Что подготовить перед оценкой разработки

**Короткий анонс:** Чтобы оценка была полезной, достаточно описать задачу, пользователей, основные действия и ограничения. Полное техническое задание на старте необязательно.

**Текст статьи:**

Запрос «нужна система для работы» слишком широк, чтобы по нему честно оценить объём и сроки. Но это не значит, что заказчику сначала нужно написать длинное техническое задание.

Для первого разговора полезнее коротко описать текущий процесс и его слабое место. Кто выполняет работу? Какие шаги повторяются? Где появляются ошибки или задержки? Какие роли будут пользоваться будущим продуктом? Есть ли важные системы, с которыми нужно обмениваться данными?

Отдельно стоит отметить ограничения: желаемый срок, особенности хранения данных, уже выбранные технологии или обязательные сценарии. По итогам обсуждения команда сможет отделить обязательную первую версию от идей, которые можно проверить или добавить позже. Так оценка становится предметным планом, а не одной цифрой без объяснений.

## English version

**Publication date:** 2026-10-13

**Title:** What to prepare before estimating a software project

**Short summary:** A useful estimate starts with the task, users, key actions, and constraints. A complete technical specification is not required at the first conversation.

**Article:**

A request such as “we need a system for our work” is too broad for an honest estimate of scope and timing. But that does not mean a client needs to write a long technical specification first.

For an initial discussion, describe the current process and where it falls short. Who does the work? Which steps are repeated? Where do mistakes or delays appear? Which roles will use the product? Are there existing systems it needs to exchange data with?

Also mention constraints: a target date, data storage requirements, technologies already selected, or scenarios that must be supported. After the discussion, the team can separate the essential first version from ideas that can be validated or added later. The result is a useful plan, not a number without explanation.
