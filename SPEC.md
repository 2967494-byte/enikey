# ТЕХНИЧЕСКОЕ ЗАДАНИЕ: Персональная система управления «Второй Мозг» (Personal ERP / CRM)

## 1. Общая концепция и Архитектура

Система представляет собой многостраничное веб-приложение (Multi-Page Application) на языке Python с серверным рендерингом страниц и готовым JSON API.

### Ключевые архитектурные требования:

1. **Многостраничная структура (MPA):** Никакого размещения всего функционала на одной перегруженной странице. Каждый раздел системы и **каждый отдельный проект имеют свой уникальный URL и собственную страницу**. Для динамического обновления отдельных блоков без перезагрузки всей вкладки (отметка задач, смена статуса заказа) используется связка **Jinja2 + HTMX**.
2. **Полная детерминированность на Этапе 1:** Вся логика (сводный календарь, автопланирование квот времени в окне 09:00–22:00, пересчет кредитов, контроль доставки деталей и предупреждения о кассовых разрывах) работает на чистых алгоритмах Python без участия нейросетей.
3. **Универсальный шлюз команд (Command Bus — задел под ИИ и iOS):** Веб-маршруты (HTML) и API-маршруты (JSON) не содержат бизнес-логики. Они передают строго типизированные `Pydantic`-схемы в единый сервисный слой (`CommandExecutor`). Это гарантирует, что:
* **На Этапе 1:** команды формируются из HTML-форм на сайте.
* **На Этапе 2 (Подключение ИИ):** любая LLM-модель получает список `Pydantic`-схем как описание инструментов (`tools`) и вызывает те же самые функции.
* **На Этапе 3 (iOS-приложение):** нативный клиент на iPhone общается с тем же бэкендом по REST API (`/api/v1/commands`).

## 2. Технологический стек

## 3. Структура Базы Данных и Шаблоны Проектов

### 3.1. Справочник локаций (`locations`)

Используется для привязки бытовых, офисных и курьерских задач к физическим точкам.

* `id` (PK)
* `name` (String) — например: `Дом`, `Офис 1`, `Офис 2`, `ПВЗ / Доставка`, `Автосервис`.
* `color` (String) — цвет метки.

### 3.2. Проекты (`projects`)

Базовая таблица для всех направлений деятельности.

* `id` (PK)
* `title` (String) — название проекта.
* `description` (Text) — общее описание, документация, заметки.
* `project_type` (Enum):
  * `IT_SYSTEM` — Сайты, сложные системы на сопровождении, доработка.
  * `NEW_IDEA` — Новые нестартовавшие проекты, идеи приложений, R&D.
  * `DIY_BUILD` — Сборка оборудования (3D-принтер, мебель, ремонт).
  * `AUTO` — Автомобиль, ТО, ремонт.
  * `LOAN` — Кредит, банк, обязательства.
  * `HOUSEHOLD` — Бытовые и офисные дела.
* `stage` (Enum): `NOT_STARTED` (Не стартовал / Идея), `ACTIVE` (Активная разработка/сборка), `MAINTENANCE` (Сопровождение), `ON_HOLD` (На паузе), `COMPLETED` (Завершен).
* `priority` (Integer: 1..4) — `1: Критический`, `2: Высокий`, `3: Обычный`, `4: Фоновый (низкий приоритет)`.
* `color_hex` (String) — уникальный цвет проекта для отображения в едином календаре.
* `weekly_quota_minutes` (Integer, default=0) — сколько минут в неделю нужно обязательно уделять проекту (например, `120` минут = 2 часа в неделю для фоновых проектов).
* `preferred_slot_minutes` (Integer, default=60) — минимальный размер слота для автопланировщика (по 60 или 120 минут).
* `template_payload` (JSON) — специфические поля конкретного типа проекта:

#### Спецификация шаблонов (`template_payload`):

| Тип проекта | Поля шаблона (JSON-структура) | Автоматические триггеры системы |

Сборка / 3D-принтер (`DIY_BUILD`)** | • `specs`: характеристики и заметки по сборке<br>• `budget_limit`: плановый бюджет сборки<br>• *Связь с таблицей комплектации `supply_items`* | • Автоматический подсчет прогресса комплектации (сколько деталей на руках, сколько в пути, сколько осталось купить).<br>• Разблокировка задачи «Собрать», когда все детали перешли в статус «На руках». |
| **4. Автомобиль (`AUTO`)** | • `car_model`: марка и госномер<br>• `current_mileage`: текущий пробег (км)<br>• `last_to_date`: дата последнего ТО<br>• `last_to_mileage`: пробег на момент ТО<br>• `to_interval_km`: регламент (например, 10 000 км)<br>• `insurance_until`: дата окончания страховки<br>• `service_log`: история работ и замен | • Вычисление остатка пробега до ТО: Остаток = (last_to_mileage + to_interval_km) - current_mileage.<br>• При остатке менее 1000 км создается задача «Пройти ТО» и бронь суммы в бюджете. |

### 3.3. Комплектация, Посылки и Заказы знакомым (`supply_items`)

Единая таблица для учета деталей 3D-принтера, покупок в дом (шкаф), автозапчастей и заказов для друзей/знакомых.

* `id` (PK)
* `project_id` (FK → `projects.id`, nullable)
* `item_name` (String) — название позиции (*«Рельсы MGN12»*, *«Шкаф в комнату»*, *«Тормозные колодки»*).
* `status` (Enum):
  1. `NEED_TO_BUY` — Осталось купить (в списке закупок)
  2. `ORDERED_IN_TRANSIT` — Купил, в пути
  3. `ARRIVED_AT_PICKUP` — Приехало в ПВЗ / Ждет курьера (нужно забрать)
  4. `IN_STOCK` — На руках (получено)
  5. `USED_OR_HANDED_OVER` — Установлено в сборку / Отдано знакомому
* `vendor` (String, nullable) — где заказано (`AliExpress`, `Ozon`, `Автодок`, `Мебельный`).
* `order_link_or_track` (String, nullable) — ссылка на заказ или трек-номер.
* `expected_date` (Date, nullable) — ожидаемая дата прибытия.
* `cost` (Numeric, default=0) — стоимость.
* **Блок поручений («Для знакомого»):**
  * `target_person` (String, nullable) — если пусто, деталь для себя. Если указано имя (*«Иван»*), это заказ для знакомого.
  * `payment_settlement` (Enum):
    * `SELF` — собственная покупка
    * `WAIT_FOR_ORDER` — знакомый попросил заказать (еще не куплено)
    * `PREPAID_BY_FRIEND` — знакомый уже перевел деньги
    * `PAID_BY_ME_DEBT` — куплено за свои деньги, нужно забрать долг при передаче
    * `CLOSED` — деталь отдана, деньги получены

### 3.4. Задачи и Календарные слоты (`tasks`)

* `id` (PK)
* `project_id` (FK → `projects.id`, nullable)
* `location_id` (FK → `locations.id`, nullable) — точка выполнения (`Офис 1`, `Офис 2`, `Дом`).
* `title` (String) — название (*«Сделать домофон»*, *«Подсоединить раковину»*, *«Собрать шкаф»*).
* `status` (Enum):
  * `BLOCKED` — Ждет доставки детали или закрытия другой задачи (скрыта из активных задач на сегодня).
  * `TODO` — Готова к выполнению.
  * `SCHEDULED` — Стоит в календаре на конкретное время.
  * `DONE` — Выполнена.
* `priority` (Integer: 1..4)
* `duration_minutes` (Integer, default=60) — длительность выполнения.
* `hard_due_date` (Date, nullable) — жесткая привязка к дате (например, «Завтра»).
* `scheduled_start` (DateTime, nullable) — дата и время начала в календаре.
* `scheduled_end` (DateTime, nullable) — дата и время окончания в календаре.
* `is_auto_placed` (Boolean, default=False) — флаг: слот поставлен автопланировщиком по квоте (`True`) или вручную (`False`).
* `depends_on_supply_id` (FK → `supply_items.id`, nullable) — связь с деталью/доставкой (например, задача *«Собрать шкаф»* зависит от позиции *«Шкаф»*).
* `depends_on_task_id` (FK → `tasks.id`, nullable) — связь с предыдущей задачей.

### 3.5. Финансы, Планировщик покупок и Дни рождения (`finance_records` и `wallet_state`)

* `wallet_state`: хранит `current_balance` (текущий фактический остаток средств) и `safety_threshold` (неснижаемый порог безопасности).
* `finance_records`:
  * `id` (PK)
  * `project_id` (FK → `projects.id`, nullable)
  * `supply_item_id` (FK → `supply_items.id`, nullable)
  * `title` (String) — описание (*«Оплата по договору»*, *«Платеж по кредиту»*, *«ДР друга»*, *«Покупка деталей»*).
  * `record_type` (Enum):
    * `INCOME_EXPECTED` — Ожидаемое поступление
    * `EXPENSE_MANDATORY` — Обязательный расход (кредиты, серверы, ТО, налоги)
    * `EXPENSE_BIRTHDAY` — День рождения / Подарок / Мероприятие
    * `EXPENSE_WISHLIST` — Планируемая покупка (необязательная / хотелка)
  * `amount` (Numeric) — сумма.
  * `planned_date` (Date) — дата события.
  * `is_annual_or_monthly` (Enum: `NONE`, `MONTHLY`, `YEARLY`) — периодичность (для ДР и абонентских плат).
  * `status` (Enum): `PLANNED` (Ожидается), `EXECUTED` (Проведено по факту).

## 4. Алгоритмы автоматизации (Бизнес-логика)

### 4.1. Автопланировщик расписания в окне 09:00 – 22:00 (`SchedulerEngine`)

Алгоритм распределяет время с учетом приоритетов, локаций и недельных квот:

1. **Доступное окно:** Ежедневно с **09:00 до 22:00** (13 часов в сутки).
2. **Учет жестких задач и локаций:**
   * Задачи с фиксированной датой (*«Завтра в Офисе 1 сделать домофон»*, *«В Офисе 2 подсоединить раковину»*) закрепляются в расписании первыми.
   * **Гео-группировка:** Если на день назначен выезд в локацию `Офис 1`, планировщик автоматически подтягивает из бэклога `TODO` другие мелкие задачи с меткой `Офис 1` в соседний временной слот, чтобы сделать всё за один визит.
3. **Распределение недельных квот (правило «Проект не важен, но 2 часа в неделю удели»):**
   * Система выбирает все проекты, у которых `weekly_quota_minutes` больше нуля (например, 120 минут).
   * Считает, сколько минут по этому проекту уже выполнено или стоит в календаре на текущей неделе (Пн–Вс).
   * Если квота не выбрана, алгоритм находит свободные окна между **09:00 и 22:00** (оставляя минимум 35% дня свободным под буфер и текучку) и ставит туда блок работы над проектом (`is_auto_placed = True`).
4. **Автоматический сдвиг:** Если авто-слот не был выполнен в запланированный день, он не превращается в «просроченный долг», а автоматически переносится на следующее свободное окно в пределах 09:00–22:00 текущей недели.

### 4.2. Логистический конвейер (Детали, Шкаф, Заказы знакомым)

1. **Заказ для знакомого:** Если добавляется запись в `supply_items` со статусом `WAIT_FOR_ORDER` и именем знакомого, создается задача: *«Заказать [Деталь] для [Имя]»*.
2. **Прибытие заказа:** Как только статус любой детали меняется на `ARRIVED_AT_PICKUP` (или наступает `expected_date`), автоматически создается задача: *«Забрать заказ: [Название] ([Магазин])»*.
3. **Получение на руки (`IN_STOCK`):**
   * Если это деталь для собственного проекта (шкаф или комплектующие 3D-принтера), система проверяет таблицу `tasks` по полю `depends_on_supply_id`. Как только все необходимые детали получены, заблокированная задача *«Собрать шкаф / Собрать узел 3D-принтера»* автоматически меняет статус с `BLOCKED` на `TODO`.
   * Если это деталь для знакомого (`target_person` заполнен), создается задача: *«Передать [Деталь] → [Имя знакомого]»* (с пометкой *«Забрать деньги: X ₽»*, если статус `PAID_BY_ME_DEBT`).

### 4.3. Финансовый радар и защита от кассового разрыва (`BudgetGuard`)

При открытии раздела финансов или при попытке запланировать новую покупку система рассчитывает прогноз на **14 и 30 дней вперед**:

$$\text{Доступный лимит} = \text{Текущий баланс} + \text{Ожидаемые поступления} - (\text{Кредиты} + \text{Серверы/SSL} + \text{Дни рождения} + \text{Обязательное ТО})$$

* **Предупреждение:** Если в ближайшие 14 дней предстоят обязательные списания или дни рождения, система выводит желтый/красный блок предупреждения: *«Внимание! Через X дней предстоят траты: [Список: Кредит, ДР, ТО] на общую сумму Y ₽. Планируемая покупка приведет к дефициту бюджета»*.

## 5. Карта страниц веб-приложения (Отдельные URL)

В системе используется левое навигационное меню и отдельные страницы под каждую сущность:

1. **`GET /` — Главный пульт и Единый Календарь**
   * Верхний ряд: Индикатор свободного бюджета на 14 дней (с предупреждениями о скорых тратах/ДР), счетчик посылок к получению и быстрые кнопки добавления.
   * Основная область: **Сводный Мастер-Календарь** (слоты с 09:00 до 22:00), где события окрашены в цвета своих проектов, + кнопка **«Авто-распределить неделю»**.
   * Правая панель: Чек-лист задач на сегодня с быстрым фильтром по локациям (`Все` | `Дом` | `Офис 1` | `Офис 2` | `Забрать заказы`).
2. **`GET /projects` — Каталог проектов**
   * Группировка по категориям (`IT и Системы`, `Новые идеи`, `Сборка / DIY`, `Авто и Кредиты`, `Дом и Офисы`).
   * На карточках отображаются приоритет, статус, индикатор недельной квоты (`Отработано 0 из 2 ч/нед`) и горящие алерты проекта.
3. **`GET /projects/{project_id}` — Индивидуальная страница проекта**
   * **Шапка проекта:** Название, описание, цвет в календаре, приоритет, настройка квоты времени (часов в неделю).
   * **Модуль шаблона (динамически зависит от типа проекта):**
     * *Для IT-проекта:* домены, SSL-таймер, серверы, памятка по доступам.
     * *Для 3D-принтера / DIY:* сводка комплектации (`Уже есть` / `В пути (где заказано)` / `Осталось купить`) с быстрым добавлением деталей.
     * *Для Авто:* текущий пробег, остаток км до ТО, страховка, история обслуживания.
     * *Для Кредита:* банк, остаток долга, график платежей, кнопка проведения очередного платежа.
     * *Для Идеи:* концепция, таблица «Кого пригласить в проект», смета запуска.
   * **Внутренний календарь проекта:** Показывает расписание и задачи строго по этому проекту (включая заблокированные задачи `BLOCKED`, ожидающие доставки).
   * **Финансы проекта:** Все поступления и расходы, связанные с этим проектом.
4. **`GET /logistics` — Сводный трекер доставок, запчастей и поручений**
   * Четыре колонки по статусам: `Осталось купить` | `Заказано (В пути)` | `Приехало (Забрать!)` | `На руках`.
   * Отдельный блок **«Заказы для знакомых»**: кому что нужно заказать или отдать, где забрать и статус расчета по деньгам.
5. **`GET /finance` — Бюджет, Ожидаемые поступления, Покупки и Дни рождения**
   * Платежный календарь (доходы vs расходы по дням).
   * Управление списком планируемых покупок (Wishlist) с автоматической проверкой на кассовый разрыв.
   * Справочник Дней рождений и регулярных платежей.

## 6. Шлюз для будущего подключения любого ИИ-агента (`app/core/commands.py`)

Все изменения данных в системе оформляются через универсальные Pydantic-команды.
Веб-формы и REST API (`POST /api/v1/commands`) вызывают `CommandExecutor.execute(cmd, db)`.
Список схем экспортируется через `GET /api/v1/tools` для LLM Function Calling.
